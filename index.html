Introduction to Deployment and CI/CD

How a website travels from your laptop to the whole world — and why teams use robots to do it.

What is deployment? The web app lifecycle

From "it works on my laptop" to "it works for everyone".

By the end of this class you can:
  • Say what "deployment" means in one sentence.
  • Name the 4 environments: development, testing, staging, production.
  • Explain why we don't edit the live website directly.

1. What is deployment?

When you open index.html by double-clicking, only you can see it. Deployment means copying your website to a computer on the internet (a server or host) so that anyone with the link can open it.

🎭 Analogy: the college annual function

You practise your dance at home (development) → your group practises together (testing) → full dress rehearsal on the real stage (staging) → the actual show in front of the audience (production). You never try a brand-new step for the first time in front of the audience!

2. The four environments

Environment Where it runs Who sees it Example URL
Development (dev) Your laptop Only you http://localhost:5173
Testing Your laptop or a CI robot Developers No public URL – automatic checks
Staging A server that copies production Team, teacher, client staging.festhub.com
Production (prod / live) The real server Everyone festhub.com
💻 Develop→🧪 Test→🎬 Staging→🌍 Production→🔁 Feedback & fix

This loop never ends. After going live, users find bugs or ask for features, and the cycle starts again. That full circle is called the web application lifecycle.

📌 Use case: the college fest website

Riya builds the fest website on her laptop (dev). She shares a staging link with the fest committee, who notice the date of "Battle of Bands" is wrong. She fixes it, and only then publishes it to the real link that 3,000 students will open (production). Nobody saw the wrong date except the committee. 🎉

3. Deploying "by hand" — and why it hurts

The old way: open a file-upload tool, drag your files to the server, hope nothing is missing. Problems:

  • 😱 You forget to upload style.css → live site looks broken.
  • 🕚 Late-night uploads, no record of who changed what.
  • 🔙 No easy way to go back to yesterday's working version.

CI/CD fixes all of these. We'll see how next week.

Why CI/CD? The three "C"s

Continuous Integration, Continuous Delivery, Continuous Deployment — in plain words.

By the end of this class you can:
  • Explain CI, Continuous Delivery and Continuous Deployment with an example each.
  • List 5 benefits of CI/CD.
  • Draw a simple pipeline diagram.

1. The problem: "integration hell"

Five students build one project. Each works alone for two weeks. The night before submission they try to combine (integrate) their code… and nothing works. Buttons are missing, CSS clashes, someone deleted someone else's function. 😵

The fix is simple: combine code often (every day) and check it automatically every time. That is CI.

2. The three "C"s

CI – Continuous Integration

Every time someone pushes code, a robot automatically builds and checks it. If something breaks, you know in minutes, not weeks.

Like a teacher checking each homework page the moment you finish it.

CD – Continuous Delivery

After CI passes, the code is always ready to go live. A human just clicks a button to release.

Like a packed pizza waiting at the counter – the manager says "send it".

CD – Continuous Deployment

After CI passes, the code goes live automatically. No button. No waiting.

Like a pizza that is delivered the moment it is packed.

Continuous Integration Continuous Delivery Continuous Deployment
Auto build & test? ✅ Yes ✅ Yes ✅ Yes
Ready to release? Not necessarily ✅ Always ✅ Always
Goes live automatically? ❌ No ❌ Human approves ✅ Yes
Good for Every project Banking, exams portal Blogs, portfolios, FestHub

3. A pipeline, drawn simply

A pipeline is the list of steps the robot runs, in order. If one step fails, the pipeline stops and tells you.

✍️ Write code→⬆️ git push→📦 Install→🔍 Lint→🧪 Test→🏗️ Build→🚀 Deploy→✅ Live!

4. Benefits of CI/CD

Benefit Meaning Example
⚡ Faster feedback Find mistakes within minutes A red ❌ appears on GitHub 2 min after you pushed a typo
🔁 Repeatable builds Same steps every time, on a clean machine No more "it works on my laptop only"
🙅 Fewer manual errors The robot never forgets a file No missing style.css on the live site
🤝 Better collaboration Everyone's code is checked the same way Teammates trust each other's pull requests
🛡️ Reliable releases Small, checked changes go live Easy to find and undo a bad change
📌 Real-world use case

Big companies like Amazon and Netflix deploy code thousands of times a day. They can only do this because robots check and release every small change. Even a one-person portfolio site benefits: you push, and 60 seconds later your site is updated.

🧑‍💻 Practice – Week 2 (group activity)
  1. For each situation, say CI, Continuous Delivery or Continuous Deployment:
    • a) Every push runs tests, but nothing is published. (CI)
    • b) A university result portal: tests pass, but the exam cell clicks "Publish" at 10 am. (Delivery)
    • c) A personal blog updates by itself after each push. (Deployment)
  2. Draw the pipeline for FestHub with boxes and arrows. Mark which step would catch: a spelling mistake in JS, a missing file, a wrong countdown result.
  3. Write 3 lines in your notebook: "Without CI/CD our team would…".
🔑 Key takeaway: CI = auto-check every change. Continuous Delivery = always ready, a human releases. Continuous Deployment = goes live by itself.

Tools of the trade: npm, build tools, hosting & risks

The little machines that make the pipeline work.

By the end of this class you can:
  • Create a package.json and run npm scripts.
  • Explain what a build tool (Vite) does and what the dist folder is.
  • Name 4 common deployment risks and how to avoid them.

1. npm and package.json

npm (Node Package Manager) comes with Node.js. It does two jobs: installs tools/libraries and runs shortcut commands called scripts. The settings live in a file called package.json — think of it as your project's ID card. 

# Inside your festhub folder: create package.json with default answers
npm init -y

# Install a tool only needed during development (-D = devDependency)
npm install -D serve

# Run a script defined in package.json
npm run start

{
  "name": "festhub",
  "version": "1.0.0",
  "scripts": {
    "start": "serve .",
    "hello": "echo Hello from npm scripts!"
  },
  "devDependencies": {
    "serve": "^14.2.0"
  }
}
File / folder What it is Push to GitHub?
package.json List of tools + scripts ✅ Yes
package-lock.json Exact versions of every tool (so everyone gets the same) ✅ Yes
node_modules/ The downloaded tools (huge!) ❌ Never – anyone can recreate it with npm install
💡 npm install vs npm ci

npm install – for you while developing; may update the lock file.
npm ci – "clean install"; installs exactly what's in package-lock.json. Robots (CI) use npm ci because it's faster and repeatable.

2. What is a build tool?

Your code is written for humans (spaces, comments, many files). A build tool turns it into a version optimised for browsers: it joins files, removes spaces (minify), and adds unique names so browsers load new versions. The result goes into a folder, usually dist/ ("distribution"). The dist folder is what gets deployed.

src: index.html + main.js + style.css→ npm run build →dist: index.html + assets/index-a1b2c3.js 
# Create a new project using the Vite build tool (vanilla = plain JS, no framework)
npm create vite@latest festhub-vite -- --template vanilla
cd festhub-vite
npm install

# Development server with live reload
npm run dev

# Make the production version (creates the dist folder)
npm run build

# Preview the production version locally
npm run preview

3. Where can a frontend live? (hosting overview)

Host Best for Free plan? Connects to GitHub?
GitHub Pages Static sites: HTML/CSS/JS, Vite builds ✅ ✅ Built-in
Netlify Static sites, forms, preview links ✅ ✅
Vercel Static sites and full Next.js apps ✅ ✅

Static = just files (HTML, CSS, JS, images). The server only hands them over. Server-rendered = the server runs code for every visitor (e.g. Next.js server features). GitHub Pages can only do static.

4. Common risks (and how CI/CD helps)

Risk What happens Prevention
❌ Failed build A typo stops npm run build; site doesn't update CI runs the build on every push and blocks bad code
🤷 Configuration differences "Works on my laptop" but not on server (different Node version, file-name case) Same Node version in CI, use npm ci, test on Linux runner
⏸️ Downtime Site is broken/offline while you upload Hosts that switch to the new version instantly; quick rollback
🔑 Exposed credentials You push an API key/password to GitHub; bots steal it in minutes .env in .gitignore, use GitHub Secrets (Week 11)
⚠️ Real story pattern

Students often push a config.js with a payment or email API key "just for testing". Automated bots scan GitHub all day for such keys. Treat any key that touched GitHub as stolen – delete/rotate it immediately.

  3. Add your own script: "info": "node -v && npm -v" and run npm run info.

🔑 Key takeaway: npm scripts are shortcuts the robot can run. The build tool creates dist/, which is what we deploy. Never push node_modules or secrets.

By the end of this class you can:

  • Create a branch, work on it and merge it.

1. The daily commands

# Copy a repo from GitHub to your laptop

cd festhub

# What changed?

# Stage + save a snapshot
git add .

# History in one line each
git log --oneline

2. Branches = parallel worlds

🌳 Analogy

main is the final notebook you submit. A branch is a rough copy where you try ideas. If the idea works, you copy it into the final notebook (merge). If not, you throw away the rough copy. The final notebook stays clean. 

# Create and switch to a new branch
git switch -c feature/countdown

# ...edit files...
git add .
git commit -m "Show hours in countdown"
git push -u origin feature/countdown

# List branches (* = current)
git branch

# Go back to main and merge the feature
git switch main
git pull
git merge feature/countdown
git push

# Delete the branch after merging
git branch -d feature/countdown
💡 Branch naming

Use clear names: feature/register-button, fix/wrong-date, docs/readme. Your teammates will instantly know what the branch is for.

3. Merge conflicts – don't panic!

A conflict happens when two people change the same line differently. Git can't guess which one is right, so it asks you. 

# On main: change the h1 text to "FestHub 2026 – Get Ready!" and commit
git switch main
git commit -am "Change title on main"

# Make a branch from the OLD commit and change the SAME line differently
git switch -c title-idea HEAD~1
# edit h1 to "FestHub 2026 – Biggest Fest Ever"
git commit -am "Change title on branch"

# Now merge into main → CONFLICT!
git switch main
git merge title-idea

Open index.html and you'll see:

<<<<<<< HEAD
  <h1>FestHub 2026 – Get Ready!</h1>
=======
  <h1>FestHub 2026 – Biggest Fest Ever</h1>
>>>>>>> title-idea
  1. Decide the final text (keep one, the other, or mix both).
  2. Delete the marker lines <<<<<<<, =======, >>>>>>>.
  3. Save, then:
git add index.html
git commit -m "Resolve title conflict"
git push
💡 VS Code helps

VS Code shows buttons above a conflict: Accept Current, Accept Incoming, Accept Both. Click one, then save.

⚠️ Top 3 beginner mistakes
  • Forgetting git pull before starting work → more conflicts.
  • Committing everything into one giant commit "final final 2". Commit small and often.
  • Working directly on main. Always use a branch for new work.

Your first robot: GitHub Actions

Workflow YAML, events, jobs, steps, runners — and a real lint/build check.

By the end of this class you can:
  • Explain workflow, event, job, step, runner and action.
  • Write a YAML workflow that runs on every push.
  • Add ESLint + build checks and read the run logs.

1. What is GitHub Actions?

GitHub Actions is a free robot inside GitHub. You give it a recipe (a YAML file) and it follows the recipe whenever something happens in your repo — like a push or a pull request.

Word Simple meaning Pizza-shop version
Workflow The whole recipe file in .github/workflows/ The order process
Event (on:) What starts it: push, pull_request… A customer places an order
Job A group of steps that run on one machine "Make the pizza" station
Step One command or one action Add cheese
Runner The fresh computer GitHub lends you (e.g. ubuntu-latest) The kitchen
Action (uses:) A ready-made step someone else wrote Ready-made pizza sauce

2. YAML in 60 seconds

  • key: value pairs.
  • Indentation = structure. Use 2 spaces, never tabs.
  • A dash - starts a list item.
  • # starts a comment.

3. Hello-world workflow

Create the file .github/workflows/hello.yml:

name: Hello Robot

# EVENT: run on every push
on: push

jobs:
  say-hello:                 # JOB name
    runs-on: ubuntu-latest   # RUNNER
    steps:
      - name: Print a message          # STEP 1 – a command
        run: echo "Hello from GitHub Actions! 🤖"

      - name: Show the date and machine
        run: |
          date
          uname -a

mkdir -p .github/workflows
# (create hello.yml in VS Code, then:)
git add .
git commit -m "Add first GitHub Actions workflow"
git push

Now open your repo on GitHub → Actions tab → click the run → click the job → expand each step to read the logs. 🟡 = running, ✅ = passed, ❌ = failed.

4. Lab: automatic lint + build check

A complete pipeline: install → lint → test → build

1. What is a test?

A test is a small piece of code that checks another piece of code gives the right answer. Example: "If the fest is on 15 Dec and today is 10 Dec, daysLeft must return 5." If someone breaks the function later, the test fails and CI shows ❌. 

npm install -D vitest

// Returns how many whole days are left until the fest
export function daysLeft(festDate, today) {
  const oneDay = 1000 * 60 * 60 * 24;
  const diff = Math.ceil((festDate - today) / oneDay);
  return diff < 0 ? 0 : diff;   // never show negative days
}

// Formats an entry fee like "₹150" or "Free"
export function formatFee(amount) {
  return amount === 0 ? "Free" : "₹" + amount;
}

import { describe, it, expect } from "vitest";
import { daysLeft, formatFee } from "./utils.js";

describe("daysLeft", () => {
  it("counts days before the fest", () => {
    expect(daysLeft(new Date("2026-12-15"), new Date("2026-12-10"))).toBe(5);
  });
  it("never goes below zero after the fest", () => {
    expect(daysLeft(new Date("2026-12-15"), new Date("2026-12-20"))).toBe(0);
  });
});

describe("formatFee", () => {
  it("shows Free for 0", () => {
    expect(formatFee(0)).toBe("Free");
  });
  it("adds rupee sign", () => {
    expect(formatFee(150)).toBe("₹150");
  });
});

"scripts": {
  "dev": "vite",
  "build": "vite build",
  "preview": "vite preview",
  "lint": "eslint .",
  "test": "vitest run"
}

npm test
# ✓ src/utils.test.js (4 tests)  → all green!

2. The full CI workflow

name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - name: Get the code
        uses: actions/checkout@v4

      - name: Set up Node.js 20
        uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm          # re-use downloads → faster runs

      - name: Install dependencies
        run: npm ci

      - name: Lint (fast, cheap check first)
        run: npm run lint

      - name: Run tests
        run: npm test

      - name: Production build
        run: npm run build
⏩ Why this order? "Fail fast"

Lint takes 2 seconds, tests 10 seconds, build 30 seconds. If there's a silly typo, why wait for the slow build? Put cheap checks first so you get bad news quickly. When any step fails, all later steps are skipped.

📌 Use case

Aman changes daysLeft and accidentally removes the "never negative" line. Lint passes (no syntax error), but the test "never goes below zero" fails ❌. Branch protection blocks his PR. The live site never shows "-5 days to go". 🙌

Triggers, tags, manual runs & artifacts

Control when the robot runs and keep what it builds.

By the end of this class you can:
  • Use push, pull_request, tag, manual and scheduled triggers.
  • Create a version tag like v1.0.0.
  • Save the dist folder as a downloadable artifact.

1. Trigger types

Trigger Runs when… Typical use
push Code is pushed to a branch CI on main, deploy on main
pull_request A PR is opened or updated Check code before merge
push: tags A tag like v1.2.0 is pushed Official releases
workflow_dispatch You click Run workflow button Manual deploy, re-deploy
schedule At fixed times (cron) Nightly checks, scheduled release 
on:
  push:
    branches: [main]
    tags: ["v*"]              # v1.0.0, v2.1.3 ...
  pull_request:
    branches: [main]
  workflow_dispatch:          # adds a "Run workflow" button
    inputs:
      reason:
        description: "Why are you running this?"
        required: false
        default: "manual check"
  schedule:
    - cron: "30 3 * * 1"      # every Monday 03:30 UTC (09:00 IST)
💡 Reading cron

5 fields: minute hour day-of-month month day-of-week. 30 3 * * 1 = minute 30, hour 3, any day, any month, Monday. GitHub uses UTC time (IST = UTC + 5:30). Try crontab.guru to check.

2. Tags = version labels

# Mark the current commit as version 1.0.0
git tag v1.0.0
git push origin v1.0.0

# See all tags
git tag

# Made a mistake? Delete a tag locally and on GitHub
git tag -d v1.0.0
git push origin --delete v1.0.0

Version numbers follow MAJOR.MINOR.PATCH: v1.0.1 = small bug fix, v1.1.0 = new feature, v2.0.0 = big change.

3. Artifacts – keep the build output

The runner computer is deleted after every run. If you want to keep the dist folder (to download it, inspect it, or deploy it in another job), save it as an artifact. 

      - name: Save build output
        uses: actions/upload-artifact@v4
        with:
          name: festhub-dist
          path: dist/
          retention-days: 7     # auto-delete after a week

After the run, scroll down on the run summary page → Artifacts → download festhub-dist.zip. Unzip it – it's exactly what would go live. 

  show-files:
    needs: build-and-test      # wait for the first job to pass
    runs-on: ubuntu-latest
    steps:
      - uses: actions/download-artifact@v4
        with:
          name: festhub-dist
          path: dist
      - run: ls -R dist
📌 Use case

The fest committee wants to approve the exact website before release. You push tag v1.0.0, the workflow builds it, uploads the artifact, and the committee downloads and checks it. The same files are then deployed — no "rebuilding and hoping".

Deployment strategies & release patterns

Not every release should go out the same way.

By the end of this class you can:
  • Compare manual, continuous, preview, staging→production and scheduled deployments.
  • Explain rolling, blue-green and canary releases with trade-offs.
  • Pick a suitable strategy for a given project.

1. Deployment strategies (how code reaches production)

Strategy How it works ✅ Good ⚠️ Watch out Example
Manual A person runs the deploy (button / command) Full control Slow, human mistakes Uploading files by hand
Continuous deployment Every merge to main goes live automatically Fast, no effort Needs good tests Portfolio, blog, FestHub
Preview deployments Every PR gets its own temporary URL Reviewers see the change Previews can leak unreleased work Netlify/Vercel PR links
Staging → production promotion Deploy to staging, test, then promote the same build to prod Safe, realistic testing Two environments to maintain College admission portal
Scheduled release Deploy at a fixed time (cron / planned) Release when traffic is low or at an announcement time Someone must watch it Results declared at 10:00 am

2. Release patterns (how users are switched to the new version)

🔄 Rolling

Many servers are updated one by one. Some users see old, some new, for a few minutes.

Like replacing the chairs in a classroom row by row while the class continues.

🔵🟢 Blue-Green

Two identical setups. Blue is live; you deploy to Green, test it, then flip all traffic to Green. Problem? Flip back.

Like two stages: the next act gets ready behind the curtain, then the spotlight switches.

🐤 Canary

Release to a small % of users first (say 5%). Watch for errors. If OK, increase to 25%, 50%, 100%.

Like the canteen trying a new dish on one table before adding it to the menu.

Pattern Downtime Rollback speed Cost / effort Best when…
Rolling None (if done right) Medium Low Many servers, small changes
Blue-Green None ⚡ Instant (flip back) High (double setup) Important launches
Canary None Fast (send everyone to old) Medium (needs monitoring) Huge user base, risky change
💡 Good news for frontend devs

Netlify and Vercel do atomic deploys: they upload the whole new version first and then switch instantly — basically blue-green for free. Old versions are kept, so rollback is one click.

3. A staging → production workflow (concept)

jobs:
  deploy-staging:
    runs-on: ubuntu-latest
    environment: staging          # auto
    steps:
      - run: echo "Deploying to staging..."

  deploy-production:
    needs: deploy-staging
    runs-on: ubuntu-latest
    environment: production       # can require a teacher/lead to click "Approve"
    steps:
      - run: echo "Deploying the SAME build to production..."

In Settings → Environments → production, add Required reviewers. The workflow will pause and wait for approval. That's Continuous Delivery in action.

    • a) Your personal portfolio site.
    • b) University exam result portal (50,000 students at 10 am).
    • c) A food delivery app changing its payment page.
    • d) FestHub during the 3 fest days.
  2. Create two environments staging and production in your repo settings, add yourself as required reviewer on production, and run the workflow above. Approve it.
🔑 Key takeaway: Strategy = when/how code reaches production. Pattern = how users switch. Blue-green = instant flip; canary = small group first; rolling = one server at a time.

Secrets, permissions, debugging & rollback

Keep keys safe, fix red builds, and undo bad releases calmly.

By the end of this class you can:
  • Use environment variables and GitHub Secrets correctly.
  • Apply least-privilege permissions in a workflow.
  • Read a failed log, fix it, and roll back with git revert.

1. Environment variables

An environment variable is a setting that changes depending on where the code runs — e.g. the API address is localhost on your laptop but api.festhub.com in production. 

VITE_API_URL=http://localhost:4000
VITE_FEST_NAME=FestHub 2026

// Vite only exposes variables that start with VITE_
const apiUrl = import.meta.env.VITE_API_URL;
console.log("Talking to:", apiUrl);

      - name: Production build
        run: npm run build
        env:
          VITE_API_URL: https://api.festhub.com
🚨 Very important: frontend code is public

Everything inside your built JS can be read by anyone (right-click → View source / DevTools). So VITE_ variables are for public settings only (API URL, site name). Never put a database password, payment secret key or private token in frontend code — even via secrets.

2. GitHub Secrets

Secrets are for things the robot needs but people must not see — like a deploy token for Netlify. Repo → Settings → Secrets and variables → Actions → New repository secret. 

      - name: Deploy to Netlify
        run: npx netlify-cli deploy --prod --dir=dist
        env:
          NETLIFY_AUTH_TOKEN: ${{ secrets.NETLIFY_AUTH_TOKEN }}
          NETLIFY_SITE_ID: ${{ secrets.NETLIFY_SITE_ID }}
Type Where to set Use for
Repository secret Settings → Secrets and variables → Actions Tokens used by all workflows
Environment secret Settings → Environments → (staging/production) Different token per environment; protected by reviewers
Variable (not secret) Same page → Variables tab → ${{ vars.NAME }} Non-sensitive settings like a URL

GitHub hides secrets in logs as ***. Secrets are not given to workflows from forked repos' PRs, to keep them safe.

⚠️ Leaked a key? Do this order
  1. Revoke/rotate the key on the provider's website first (make it useless).
  2. Create a new key and save it as a GitHub Secret.
  3. Remove it from the code and commit. (It's still in history – that's why step 1 matters most.)

3. Least privilege permissions

Give the robot only the permissions it needs — like giving a delivery boy the gate key, not the house locker key. 

permissions:
  contents: read      # can read the code, nothing more

4. Troubleshooting failed jobs

Method: Actions tab → red run → red job → first red step → read the last 10–20 lines. The real error is usually near the bottom.

Error in log Likely cause Fix
npm ci … can only install with an existing package-lock.json Lock file not committed / out of sync Run npm install locally, commit package-lock.json
Could not resolve "./Logo.png" (works on Windows!) Linux is case-sensitive: file is logo.png Match file name case exactly
sh: eslint: not found Tool not in devDependencies npm install -D eslint and commit
Invalid workflow file … line 12 YAML indentation / tab Use 2 spaces, check alignment
'x' is assigned a value but never used ESLint rule Remove or use the variable
Unsupported engine / syntax error only in CI Different Node version Set same node-version as your laptop
Resource not accessible by integration / 403 Missing permission Add the needed permissions: entry

Use Re-run jobs → Re-run failed jobs for temporary glitches (network timeouts). For real errors, fix the code and push again.

5. Rollback & recovery

# Find the bad commit
git log --oneline
# a1b2c3d Change countdown (bad!)
# 9f8e7d6 Add events list

# Create a NEW commit that undoes it (history stays safe)
git revert a1b2c3d
git push
# → CI runs → the good version is deployed again ✅
✅ git revert

Adds an "undo" commit. Safe for shared branches. Use this.

❌ git reset --hard + force push

Rewrites history; breaks teammates' copies. Avoid on main.

Other ways: redeploy an older tag with workflow_dispatch, or in Netlify/Vercel open Deploys → choose an older deploy → Publish / Promote (instant).

📌 A simple rollback plan (write it in your README)
  1. Notice: site broken / error reports.
  2. Roll back: promote previous deploy (1 min) or git revert (3 min).
  3. Verify the live site works.
  4. Find the cause calmly, fix it on a branch, PR, re-deploy.

🔑 Key takeaway: Public settings → env vars. Robot-only keys → Secrets. Minimum permissions. Read the last lines of the red step. Roll back with git revert or the host's previous deploy.

        uses: actions/deploy-pages@v4

2. Custom domain, DNS & HTTPS

📒 DNS = the internet's phone book

Humans remember festhub.in; computers need an IP address like 185.199.108.153. DNS looks up the name and gives the number.

Record Points a name to… Example
A An IP address festhub.in → 185.199.108.153
CNAME Another name www.festhub.in → username.github.io

Steps: buy a domain (registrar) → add the domain in your host's settings (GitHub Pages: Settings → Pages → Custom domain) → add the A/CNAME records the host shows you at your registrar → wait (minutes to a few hours) → turn on Enforce HTTPS. 

nslookup festhub.in
nslookup www.festhub.in

HTTPS = the 🔒 lock. Traffic is encrypted so nobody on college Wi-Fi can read or change it. GitHub Pages, Netlify and Vercel give free certificates automatically.

3. SPA route fallback

In a Single Page App (React Router etc.), /events is not a real file — JavaScript draws it. Clicking a link works, but refreshing /events asks the server for a file that doesn't exist → 404. Fix: tell the host "for any unknown path, send index.html".

Host Fix
Netlify File public/_redirects containing /* /index.html 200
Vercel vercel.json with a rewrite (below)
GitHub Pages Copy index.html to 404.html after build (or use hash routes /#/events) 
{
  "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }]
}

      - run: npm run build
      - run: cp dist/index.html dist/404.html

4. Asset paths & cache

🖼️ Asset paths
  • /logo.png = from the domain root → breaks on username.github.io/festhub/
  • Put images in public/ and let Vite's base handle it, or import them in JS
  • Remember: Logo.PNG ≠ logo.png on servers
🗄️ Cache
  • Browsers save files to load faster next time
  • Vite names files like index-4f9a2c.js; a new build = new name, so users get the new version
  • index.html is checked fresh; if you still see old content, press Ctrl + Shift + R (hard refresh) or use Incognito

GitHub Pages ❌ Static only Use output: "export" → upload out/ 
/** @type {import('next').NextConfig} */
const nextConfig = {
  output: "export",              // build plain HTML files into out/
  basePath: "/festhub-next",     // your repo name (project site)
  images: { unoptimized: true }, // no image server on Pages
};

export default nextConfig;

npx create-next-app@latest festhub-next
cd festhub-next
npm run build     # with output: "export" → creates out/
# In deploy.yml change:  path: dist   →   path: out
⚠️ Static export limits

No API routes, no server-side rendering per request, no middleware. If your app needs those, deploy to Vercel or Netlify instead.

3. Production verification checklist

"The pipeline is green" does not always mean "the site works". After every important deploy, a human checks. Tick these on your own live site: 

# Is the site up? Look for "HTTP/2 200"
curl -I https://USERNAME.github.io/festhub/

# Does an inner route return 200 (not 404)?
curl -I https://festhub.netlify.app/events

# Which commit is live? (shows recent deploy runs, needs GitHub CLI)
gh run list --workflow=deploy.yml --limit 3
📌 Use case

The pipeline was green, but the live FestHub showed "Talking to: http://localhost:4000" in the console – the production API URL was never set. The checklist caught it in 2 minutes, before the fest registration opened.

### Secrets used
- none (GitHub Pages uses the built-in token)

### Rollback plan
1. `git log --oneline` → find the bad commit
2. `git revert <hash>` → `git push`
3. Wait for deploy → verify the live site

3-minute demo script

  3. Break it: show a failed check on a PR and how the log points to the error (45 s).
  4. Merge a good PR → show the deploy job → refresh the live site (30 s).
